# Weekly discovery: a healthy file is not necessarily a complete backup

Date: November 13, 2026, America/Denver. Base: upstream main
`d940222c18c6a35a3d42843c735e6d9c4122695b`. This is an independent, unreleased
development patch. The November 6 exact-key lookup PR #6 remains open and is not
included or merged here.

## Discovery before implementation

Observation: MemKernel uses SQLite WAL. Recently committed records may reside in
the WAL while agent connections remain open. Hypothesis: a copy of the main file
could look healthy yet be incomplete, so checking that copy's SQLite integrity
would not be enough to establish recovery.

We initialized a disposable database, checkpointed its schema, kept an agent
connection open and appended 20 decisions. Copying only the main file produced a
database with `PRAGMA integrity_check = ok` and **zero events**, while the source
had **20 committed events** and a 424,392-byte WAL. The corrected experiment
completed cleanly on Windows / Python 3.11.0 / SQLite 3.38.4 before implementation.

**Aha:** structural health and completeness are different properties. A familiar
health check can give false confidence in a backup missing every recent decision.
That finding led to the smallest useful recovery feature: a verified online copy
into a new local file. It is new to this weekly ledger, not a global novelty claim.

SQLite documents its [online backup API](https://sqlite.org/backup.html) for
consistent copies while other users continue operating. Forum feedback favors
individual cross-device records with clear authorship; this patch instead solves
local recovery and does not enable database-file synchronization or network
sharing. See the [original discussion](https://forum.cursor.com/t/memkernel-shared-branchable-memory-for-cursor-and-other-coding-agents/175026).

## Implementation and acceptance

`memkernel backup DESTINATION [--project ...] [--db ...]` opens an existing source
read-only. SQLite online backup includes committed WAL contents. A private sibling
temporary file receives the copy, followed by structural, foreign-key and every
branch's event hash checks. The standalone file is flushed and published through
an atomic hard link that cannot replace another file. Copying has a 30-second
deadline; branch verification adds time. Preparation is shielded and drained on
cancellation before removing the temporary file, including repeated cancellation.

This reuses the standard-library SQLite API, existing private-permission helper,
schema version, branch verifier and CLI discovery. No new dependency, migration,
MCP filesystem tool, restore-over-existing command or data-sharing path is added.
The destination must be an existing directory under the operator's control on a
filesystem supporting private permissions and hard links.

Acceptance tests exercise all-table preservation, snapshots, fork/rollback audit
history, notices, leases and sync state; current branch-state comparison after
reopening; an active uncommitted writer; no-overwrite publication races; source
sidecar protection; missing source; private-permission failures; invalid schema,
foreign keys and hashes; copy timeout; single/repeated copy cancellation and
repeated verification cancellation. A Windows source path with URI delimiters is
also exercised. Source memory remains writable after backing up.

## Paired before/after evidence

Run `python benchmarks/backup_consistency.py` from an installed checkout. Five
isolated trials use identical 20-decision workloads with the agent connection
held open. Each trial compares a plain main-file copy with the actual new CLI.
The resulting online copy is reopened read-only, its branch hashes checked and
its materialized state compared with the source. All data is synthetic.

| Across five trials | Plain main-file copy | Online backup |
|---|---:|---:|
| Expected committed events | 100 | 100 |
| Retained committed events | 0 | 100 |
| Retention in this controlled workload | 0% | 100% |
| Copies passing SQLite integrity check | 5/5 | 5/5 |
| Copies matching committed event count | 0/5 | 5/5 |

Raw results: [backup-consistency-2026-11-13.json](backup-consistency-2026-11-13.json).
This is a recovery-correctness comparison, not a general claim that plain copies
always lose everything, or a speed/agent-quality improvement. When the source is
closed or checkpointed, a plain copy may include more or all data. Writes made
after the backup's captured state are outside that copy. No timing percentage is
claimed; no real user database, paid model, cloud service or network peer was used.

The backup suite adds 21 cases to main; 20 pass locally and the symlink case skips
when the host disallows creating symlinks. Main's 189 passing cases remain passing;
its three existing live/model/platform-specific skips remain explicit. Final
cross-platform GitHub CI evidence is recorded in the PR.

Current pip-audit 2.10.1 checked 86 installed third-party packages with no known
advisories. Bandit 1.9.4 adds no alerts relative to the 0.3.1 audit: zero high,
seven existing medium constant-SQL alerts and three existing low internal-assert
alerts. These are scanner observations plus a focused diff review, not a full
penetration test or enterprise certification.

The change stays within the existing local OS trust domain. Caller-supplied paths
are operator choices, not MCP inputs; source URI construction escapes delimiters;
SQL is constant; no stored memory is executed. Parent directories must be trusted.
Web authentication, UI checks, network-tenant isolation, infrastructure deployment
and schema migration gates do not apply to this bounded local backup utility.
Existing independent review and test/release procedures apply; no architectural
redesign is introduced.

The backup is **not encrypted** and includes all local database history, coordination
and sync identity/counter/audit data. It omits external keys, policies and client
configuration. Do not run it alongside the original as a duplicate syncing peer;
restoring old counters and identities needs a separate recovery design. Internal
hash consistency does not establish truth or authenticity against an external
checkpoint. See [backup and recovery instructions](../backup.md).

Not performed: merging, releasing, deployment, destructive restore, key recovery,
selective peer sharing, huge-database/long-duration soak, real-model evaluation or
desktop GUI tests. Abrupt termination can leave private temporary files. Future
work can rehearse sync identity recovery and measure large-database verification
cost before adding a restore workflow or tuning copy limits.
