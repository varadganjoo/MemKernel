# Weekly discovery: compact history still needs selective recall

Date: November 6, 2026 (America/Denver). Base: main
`d940222c18c6a35a3d42843c735e6d9c4122695b`. This is an unreleased additive
development patch, not a deployment or a new package release.

## Observation, hypothesis and experiment

The roadmap asks for compact relevant recall. The current `query_state` returns
every current decision and fact. Could more aggressive GC alone make a one-key
question cheap? We tested that assumption before implementing a new API.

A disposable synthetic database held 100 decision keys with two revisions each.
GC retained zero raw events and compacted all 200 events. Serialized kernel
`query_state` fell from 53,174 to 27,611 UTF-8 bytes, and rendered context fell
from 24,963 to 12,662 bytes using the offline byte estimator. The current values
and provenance survived. But the answer still carried all 100 decisions, even
when the caller wanted only `component.0.storage`.

**Discovery / aha:** compaction shrinks history; selection narrows an answer.
Preserving every durable decision is valuable, but also means compaction cannot
remove unrelated decisions from a one-key answer. This finding is new to our
weekly work; it is not a claim of worldwide novelty. It suggests a small useful
step before a larger relevance-ranking system: exact-key recall.

Forum feedback also favors individual decisions/facts over whole branches and
asks who wrote them. That supports the product direction, but this experiment
and patch concern local retrieval, not network sharing. See the
[Cursor discussion](https://forum.cursor.com/t/memkernel-shared-branchable-memory-for-cursor-and-other-coding-agents/175026).

## Change and acceptance

`memkernel_lookup_memory(key, kind="decision", branch_id=None)` returns one current
record with author/source event, or `record: null` for absence. A null-valued fact
remains distinguishable from an absent fact. The Python kernel and agent client
expose the same operation. Omitted branches follow the MCP/client active branch.
Explicit branch reads preserve fork ancestry, rollback and compaction semantics.
All string keys are exact, including existing blank fact keys. Missing branches
and invalid kind/key types are errors.

The implementation reuses `context_events` and `materialize`, with no new schema,
dependencies, indexes, caches, writes or data sharing. Existing tools are unchanged.
The new MCP tool is explicitly allowed in read-only sessions. Its description and
server instructions retain startup/coordination checks: this lookup omits notices
and blockers, and stored values remain untrusted assertions.

## Matched response measurements

Run `python benchmarks/lookup_memory.py` from a virtual environment with the
checkout installed. Windows, Python 3.11.0, MCP 2.3.0, cached `cl100k_base` tokenizer.
The same read-only stdio session answers 20 known-key questions by full recall and
by lookup, alternating order, before and after GC. Each answer is checked against
its expected current value, author, event and superseded event. Both methods
returned the correct record for all 20 questions in each phase.

| Measure, mean per question | Full recall before GC | Full recall after GC | Lookup, either phase |
|---|---:|---:|---:|
| Serialized MCP result bytes | 128,055 | 74,921 | 749.1 |
| Serialized MCP result tokens | 36,303 | 22,703 | 230 |
| Text content tokens | 15,929 | 9,729 | 100 |

After compaction, lookup reduced serialized result bytes by **99.0%** and result
tokens by **99.0%** for these one-key questions. Text-only tokens fell **99.0%**.
This saves response context by omitting unrelated information; full recall is
still required when that information matters. The entire `CallToolResult` is
serialized, including both text and structured output where the SDK supplies
both. JSON-RPC framing, tool schemas and conversation history are excluded.
Clients may consume only part of that result, hence the separate text measure.

Observed median call latency after GC was 10.701 ms for full recall and 5.918 ms
for lookup. These are a single workstation run, not a general speed claim.
Lookup still materializes the entire state; it is not an indexed O(1) storage
operation or a hard response budget. Large individual values remain large.

Raw measurements: [lookup-memory-2026-11-06.json](lookup-memory-2026-11-06.json).
These controlled known-key checks do not evaluate a model discovering keys,
semantic relevance, task completion, unknown-key questions, or real-world usage
frequency. No model calls, paid services or peer transport were used.

## Limits and follow-ups

Unknown-key discovery and task ranking need a separate retrieval experiment.
Selective peer export should preserve the same record/source distinction but
needs an explicit disclosure/trust design. This change does not add transport,
freshness or truth verification, distributed leases, or automatic sharing.
Production deployment, release publishing, model-quality evaluation, desktop GUI
automation and prolonged device soak are outside this weekly patch.
